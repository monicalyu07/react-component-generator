# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 1. 적용 기준

### TDD를 **반드시** 적용하는 대상
- **비즈니스 로직**
- **API** (엔드포인트, 핸들러, 외부 호출 래퍼)
- **유틸 함수**
- **버그 수정** (재현 테스트를 먼저 작성하고 실패를 확인한 뒤 고친다)

### TDD가 불필요한 대상
- **타입 정의**
- **설정 파일**
- **순수 UI** (로직 없는 마크업/스타일)
- **SQL** (스키마, 마이그레이션)

판단이 애매하면 **적용 대상으로 간주**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"**이어야 한다. 오타, import 오류, 설정 문제로 인한 실패는 RED가 아니므로 먼저 고친다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### GREEN — 통과시키는 최소 코드
- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체를 실행해 확인한다.

### REFACTOR — 정리
- **중복 제거, 이름 개선, 헬퍼 추출**만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작은 다음 RED에서 시작한다.

### 반복
- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

**테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**

- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 삭제한 코드를 보면서 테스트를 쓰면 테스트가 구현에 끌려간다. 요구사항에서 출발해 테스트를 쓴다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 30초면 쓴다. 단순한 코드가 깨지는 순간이 가장 늦게 발견된다. |
| "테스트는 나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과하므로 아무것도 증명하지 못하고, 실제로는 거의 쓰이지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD가 더 빠른 경로다. |
| "이미 짠 코드를 삭제하면 낭비다" | 매몰 비용이다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이다. 삭제하고 RED부터 시작한다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트 없이 만들어도 되지만, 그렇다면 커밋하지 않고 버려야 한다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 **`CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 그 규칙이 우선**한다.
- **이 파일은 기본값(fallback)이다.** 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
- 우선 적용되는 프로젝트 규칙이 있어도, 그 규칙 안에서는 이 문서와 같은 수준으로 엄격하게 따른다.
