# commit

변경사항을 분석해 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지를 작성한 뒤 **사용자 승인을 받고** 커밋한다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경/추가/삭제된 파일을 확인한다.
- `git diff`(unstaged), `git diff --staged`(staged)로 실제 변경 내용을 읽는다. untracked 파일은 내용을 직접 확인한다.
- `git log --oneline -10`으로 기존 커밋 스타일을 참고한다.
- 변경사항이 없으면 그 사실을 알리고 종료한다.

### 2. 논리적 단위로 분류
- 하나의 목적(기능 추가, 버그 수정, 리팩터링, 설정 변경 등)을 하나의 커밋으로 묶는다.
- 서로 다른 목적의 변경이 섞여 있으면 여러 커밋으로 나누고, 커밋별로 포함할 파일을 명시한다.
- `.env`, 키, 토큰 등 비밀 정보나 `node_modules`, 빌드 산출물처럼 커밋하면 안 되는 파일은 제외하고 사용자에게 알린다.

### 3. 커밋 메시지 작성
형식: `<type>: <한국어 요약>`

| type | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 코드 구조 개선 |
| chore | 설정, 빌드, 의존성, 문서 등 기타 작업 |

규칙:
- 요약은 한국어로, 50자 안팎의 간결한 한 줄로 쓰고 마침표를 붙이지 않는다.
- "무엇을 했는지"가 드러나게 쓴다. (예: `feat: 컴포넌트 생성 폼에 props 입력 기능 추가`)
- 필요하면 빈 줄 뒤에 본문으로 "왜" 변경했는지 덧붙인다.

### 4. 사용자 승인 후 커밋
- 분류 결과(커밋별 파일 목록 + 메시지)를 사용자에게 보여주고 **승인을 요청**한다. 승인 전에는 `git add`/`git commit`을 실행하지 않는다.
- 승인되면 커밋 단위마다 해당 파일만 `git add <파일>`로 스테이징하고 `git commit`한다. (`git add -A`/`git add .`는 피한다.)
- 사용자가 메시지나 분류를 수정하라고 하면 반영한 뒤 다시 승인을 받는다.
- 커밋 후 `git log --oneline`으로 결과를 보여준다.

## 주의
- 사용자가 명시적으로 요청하지 않는 한 `push`, `--amend`, `--no-verify`는 하지 않는다.
- pre-commit 훅이 실패하면 원인을 수정하고 새 커밋을 만든다.
